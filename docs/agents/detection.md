# Детекция: окно, состояния, статусы, модалки (задачи 3.3–3.6)

> Детальный справочник по слою `l2core/detector/`, вынесенный из AGENTS.md
> (прогрессивная загрузка: AGENTS.md — ядро, этот файл — детали по слою).
> Правится вместе с кодом: обновление затронутых заметок `docs/agents/` —
> часть DoD ломающих задач (см. «Правила изменений» в AGENTS.md).

Детекция окна и состояний, статусы окна
(`not_found / occluded_or_unstable / found`), перехватчик модалок.

## Детектор якоря (3.3, anchor.py)

numpy-only `detect_window()` (яркие линии рамки — первый дешёвый этап
для «Обзора лавок», ~27 мс/кадр) + подтверждение/поиск template matching'ом
(заголовок лавок, целое окно обзора); кэша позиции между кадрами нет —
свежий поиск на каждом grab.

## Детектор состояний (3.4, states.py)

Классификация (window, params) по кадру+якорю; состояние подтверждается
строгим совпадением ВСЕХ сигнатур (валидатор 2.3 гарантирует ≥2), оценка
в иерархии «пиксель-пробы → template → OCR» с остановкой состояния на
первом провале; OCR-клиент (`read(region_img) -> (text, confidence)`) —
опциональная инъекция, без него состояния с OCR-сигнатурами дают
unknown+диагностику (деградация, не исключение); конфликт/неподтверждение
→ unknown с журналированием конфликтующих признаков; состояния с
префиксом `recover_` (глобальный recover 5.8) классификацией не
занимаются. Публичная оценка произвольных проверок —
`StateDetector.evaluate(checks, frame, anchor)` (та же
семантика/пороги, что у сигнатур; точка переиспользования run_checks
сборки API 7.1); шаблоны проверок грузятся лениво с кэшем на экземпляре —
verify-наборы переходов могут ссылаться на элементы вне сигнатур
состояний. Порог template-сигнатур 0.9 — замер 3.4 (позитивы ≥0.998,
макс. ложный дискриминирующий 0.829).

## Детектор статусов (3.5, status.py)

Статусы `not_found / occluded_or_unstable / found` + признак «контент
прогрузился». Компонент поверх находилки окна игры (3.2) и детекторов
якоря/состояний: not_found — окно игры недоступно (причина из 3.2) или
якорь устойчиво отсутствует; occluded_or_unstable — результаты детекции
якоря различаются между двумя кадрами подряд (anchor_lost /
anchor_appeared / anchor_moved сверх допуска position_tolerance=8 px,
допущение); found — якорь стабилен. Перекрытие тултипом/окном из одного
када не детектируется (честный минимум — нестабильность между кадрами).
Контентные сигнатуры — сигнатуры не-recover состояний, кроме
элемента-опоры якоря (StateDetector.check_content, exclude_elements
передаёт статус-детектор из своего anchor_templates — должен совпадать
с опорами AnchorDetector); заголовок не считается контентом, флаг в
формат модели не добавлен (отчёт 3.5). Граница инварианта «кэша позиции
нет»: поиск якоря на каждом кадре свежий, внутреннее состояние — только
факт результата предыдущего кадра для сравнения стабильности (монитору
история разрешена, design.md решение 8).

## Перехватчик неизвестных модалок (3.6, modal.py)

Консервативная эвристика `modal.unknown` (окно игры есть, ни один якорь
не найден, в центральной области клиента — крупный яркий
прямоугольный регион) → PNG-снимок + JSONL-строка в log_dir + событие
modal.unknown; recover-исполнителя нет (5.8) — точка входа on_unknown.
На 39 кадрах сырья не стреляет (ни шума, ни позитивов — сырьё модалок
не содержит; R4, отчёт 3.6, досъёмка реальных модалок —
OWNER_QUESTIONS Q20).

## Транзакция кадра (3.6, transaction.py, design.md решение 18)

FrameTransaction(Screen) — явный контекстный менеджер, один grab
анализируется один раз (кэш по идентичности кадра, не по времени),
refresh()/reverify(predicate) — свежий grab + re-verify перед
необратимым; вложенный вход — RuntimeError. Инфраструктура для
примитивов 5.x, исполнителей здесь нет.

## Template matching (задача 3.3, решение 13)

Вид поиска — NCC, эквивалент OpenCV `TM_CCOEFF_NORMED`. Реализация по
умолчанию — `OpenCvTemplateMatcher` (`default_matcher()`): замер на всех
39 скриншотах `base_screenshot/scr/` показал полную эквивалентность
решений с numpy-only альтернативой (0 расхождений find_anchor по 3 окнам
× 39 кадров), но numpy-only в 2.3–4 раза медленнее на кадре 1920x1080
(jak 198x29: ~237 мс против ~58 мс; целое окно 1008x674: ~183 мс против
~80 мс; полный проход детекции: 26.7 с против 9.8 с; CPU, один поток) —
ощутимо хуже на горячем пути. `NumpyTemplateMatcher` остаётся встроенной
альтернативой (FFT + интегральные изображения), guard-тесты следят за
паритетом решений и score. Числа и протокол — в отчёте 3.3.
