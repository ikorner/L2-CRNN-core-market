# Дизайн: ядро «L2 Core Market» — UI-драйвер трёх торговых внутриигровых окон Lineage 2

Дата: 2026-11-08. Статус: на ревью (builder-check пройден, открытые вопросы закрыты).
Связанные проекты: `E:\L2-CRNN-arduino` (HID-управление), `E:\L2-CRNN-MODEL-TRAIN` (CRNN-OCR).

## 1. Намерение и зачем

Большой бот для торговли в Lineage 2 разбит на модули. Этот документ — ядро:
драйвер трёх внутриигровых окон: **«Обзор лавок» (market)**, **«Торговая лавка (Купить)»
(shop_buy)**, **«Торговая лавка (Продажа)» (shop_sell)**. Ядро знает состояния и контролы
окон, выполняет действия с проверкой результата и отдаёт модулям торговли стабильный API.

Стратегии торговли, списки предметов, целевые цены, маршрутизация — **вне ядра**,
отдельными сменными модулями. Ядро не знает, ЧТО покупать/продавать; оно знает, КАК
нажать «Начать продажу» и убедиться, что сделка состоялась.

Зачем так: патч игры или смена стратегии не должны ломать код. Всё знание об UI
вынесено в машиночитаемую UI-модель; ядро — её интерпретатор плюс набор примитивов.

## 2. Цели / не-цели / анти-цели

**Цели (DOD):**
- Ядро стабильно работает: каждое действие верифицируется, любой сбой ведёт в
  диагностируемый recover, а не в слепые клики.
- Легко расширять: новый элемент/состояние/окно = правка UI-модели (в общем случае
  без кода); новая фича = примитив или сценарий поверх примитивов.
- Прогон без железа: любой сценарий воспроизводится на записанных скриншотах
  (replay) без arduino и игры — для тестов и отладки.
- Интерфейсы для модулей торговли: синхронный Python API + события (push и pull).

**Не-цели (v1):**
- Стратегии, ценообразование, списки предметов, аналитика.
- Открытие чужих лавок из обзора — не возможно (обзор = только разведка цен).
- Вывеска и История: кнопки известны модели, сценарии не пишутся.
- Мультиклиент: один бот — один компьютер — одно окно игры.
- Отдельный OCR-сервис (разъём под него закладываем, реализация — потом).

**Анти-цели (что считается провалом):**
- `sleep()` вместо ожидания по предикату.
- Абсолютные экранные координаты вне слоя привязки к окну (якорь ищется каждый кадр).
- Клики без verify; OCR-вызовы мимо контракта.
- Состояние, из которого нет выхода в recover; unknown без алгоритма восстановления.

## 3. Подходы (выбран C)

- **A. Полный интерпретатор** — вся логика переходов/verify/on_fail в декларативной
  модели, ядро generic. Отвергнут: собственный DSL предикатов — это отдельный проект
  со своими тестами; для трёх окон overengineering.
- **B. Код-first** — вся логика в Python, в конфиге только rect'ы/шаблоны. Отвергнут:
  патч игры ломает код ядра, расширяемость ниже требований DOD.
- **C. Гибрид (выбран).** Модель отвечает на «где и как выглядит»: окна, элементы,
  rect'ы от якоря, визуальные варианты (normal/active/disabled), сигнатуры состояний,
  OCR-регионы, простые переходы. Код отвечает на «что делать»: примитивы
  (`wait_state`, `click_element`, `ocr_region`, `enter_price`…) и сценарии со сложной
  динамикой (скан таблицы со скроллом, рандомизированный выбор способа ввода).

## 4. Зафиксированные решения (из обсуждения)

1. **API для стратегий** — синхронный blocking-вызовы плюс события в двух формах:
   callback-подписка и блокирующий `wait_event(type, timeout)` (pull). Стратегия
   выбирает стиль сама.
2. **OCR** — в-процесс: в ядро вендорится замороженная копия инференса из
   `L2-CRNN-MODEL-TRAIN` (preprocess + CTC-декодер + загрузка чекпоинта,
   байт-идентично обучению, guard-тесты на эталонах); `crnn_best.pt` — вне git,
   путь в конфиге. Torch грузится один раз; на этом компьютере GPU, на других —
   авто-детект устройства, CPU-режим обязан работать. Контракт:
   `read(region_img) -> (text, confidence)`. Интерфейс `OcrClient` позволит позже
   подменить реализацию на удалённый сервис без правки ядра.
3. **Одно окно игры**, оконный режим, окна торговли двигаемые мышью → якорь окна
   ищется на каждом кадре, кэша позиции между кадрами нет.
4. **Разрешение**: референс 1920×1080 (под него все rect'ы). Окна торговли **не
   масштабируются** при изменении размера окна игры — масштабный коэффициент не нужен.
   Клиентская область окна игры определяется через Win32 (`pygetwindow`/win32gui по
   заголовку), окно торговли внутри — поиском якоря (template matching по заголовку
   окна). Все координаты элементов 1:1 от якоря своего окна.
5. **Фокус**: перед каждым действием проверяем, что окно игры активно и не перекрыто;
   если нет — активируем через Win32 (SetForeground). Не удалось — recover/пауза.
6. **MVP-сценарии** (для модулей торговли): обход обзора лавок (табы, фильтры,
   поиск, скролл, чтение строк), выставление своей лавки на продажу, мониторинг своей
   лавки. Продажа детектится перечитыванием окна лавки (OCR количества/прибыли со
   сравнением снимков), не чатом.

   **Уточнение ролей окон (критично):** чужие лавки из обзора НЕ открываются —
   «Обзор лавок» — только разведка цен. Оба окна «Торговая лавка» — выставление
   СВОИХ лавок: shop_buy = лавка-выкуп (твои цены закупки), shop_sell = лавка
   продажи. Стратегия-маркетмейкер: выкуп дороже всех, продажа дешевле всех,
   прибыль с разницы. Перенос предметов в лавку и обратно — drag (подтверждено
   владельцем). Поиск применяется и Enter, и кнопкой «Поиск» — способ выбирается
   рандомизацией поведенческого профиля (антидетект).
7. **Ввод цены/текста**: ядро само выбирает способ ввода — клики по экранному нумпаду
   или ввод с клавиатуры — по настраиваемому распределению (антидетект). Проценты и
   поведенческие джиттеры — в конфиге.
8. **Модалки**: универсальный перехватчик «всплыло неизвестное окно» → снимок, лог,
   recover. Конкретные типы модалок добавляются в модель по мере досъёмки (пользователь
   доснимает и размечает).
9. **Тайминги**: конфигурируемые консервативные таймауты (единицы секунд); точные
   замеры — позже по логам, значения подменяются конфигом.
10. **Kill switch**: локальный хоткей на компьютере бота (слушаем клавиатуру, не через
    arduino) + глобальный таймаут неактивности; при срабатывании — мгновенный стоп
    цикла и безопасное состояние HID.
11. **Репозиторий**: `E:\L2-CRNN-core-market`. Язык — Python 3.10+, код и комментарии
    на русском (как в arduino-модуле). Тесты — pytest.

Слои (зависимости только вниз):


### 5.1 UI-модель (`ui_model/` в репо ядра)

YAML-файлы (или JSON, решает исполнитель — YAML читаемее): одна модель на окно +
общий словарь. Секции:
- `window`: якорь (шаблон заголовка), способ поиска, вложенность относительно окна игры.
- `elements`: карточка элемента — id, rect (x, y, w, h от якоря окна), варианты
  (normal/active/disabled/…), кроп-шаблоны на вариант, click_point, роль
  (click_target, ocr_region, state_signature, icon_sample), способ ввода.
  Элементы описывают не только контролы окон, но и **HUD игры**, нужный для
  навигации: иконка открытия «Обзора лавок» (`market_pic`), иконки открытия своих
  лавок (`open_buy_trade`, `open_sale_trade`) — кропы уже есть в мете (scr_153511).
  HUD-элементы **не привязываются к фиксированным смещениям** от клиентской области:
  панели игры пользователь может перетаскивать. Иконки ищутся template matching'ом
  по клиентской области (как якорь окна), допустимая область поиска задаётся в модели.
- `states`: сигнатуры визуальные — иерархия от дешёвых к дорогим: пиксель-пробы →
  template matching → OCR-строки. Минимум два независимых признака на состояние.
- `transitions`: простые переходы `(state, action) -> (ожидаемое состояние, verify,
  timeout, on_fail[])`.
- `ocr_regions`: регионы чтения (цены, количества, заголовки колонок, строки таблицы)
  с грамматикой ожидаемого результата (digits, price, text).

**Параметризованные состояния**: детектор возвращает не имя состояния из огромного
списка, а `window=market.list, params={tab, global_filter, filter, search, scroll_pos…}`.
Комбинаций таб×фильтр×поиск×скролл сотни; именованными состояниями их не покрыть.
Стратегиям важны значения параметров. Сигнатуры окна (какое окно открыто) отделены от
значений параметров (какой таб активен — по active-кропам, образцы уже есть в мете).

**meta.json — сырьё, не зависимость.** Пишется конвертер/валидатор: подтягивает
кропы из `base_screenshot/scr/`, собирает карточки элементов, проверяет, что все
rect'ы вписываются в окно и что у каждого состояния есть сигнатуры. UI-модель в репо
самодостаточна: без меты и скриншотов ядро работает (шаблоны — единственная
связь: модель ссылается на файлы кропов либо хранит их в `assets/` ядра; решение
за исполнителем, предпочтительно — копировать нужные шаблоны в `assets/`, чтобы ядро
не зависело от структуры папок датасета).

### 5.2 Детекция состояний и окон

Каждый кадр (по запросу примитивов, не сплошной поток):
1. Найти окно игры (Win32: заголовок, клиентская область; проверить не свёрнуто).
2. Внутри — найти окно торговли по якорю (template matching по заголовку «Обзор
   лавок» / «Торговая лавка»). Не найдено → состояние `no_window`.
3. По сигнатурам определить окно и параметры; несовпадение с ожиданием → `unknown`.
4. Перехватчик модалок: внешний контур/текст, не принадлежащий известным окнам →
   `modal.unknown` → снимок в лог, recover.

### 5.3 Протоколы действий

- Никаких `sleep`: только `wait_until(predicate, timeout)`; таймауты из конфига.
- Каждое действие: `verify` (после клика по вкладке — проверка, что она стала active).
- При verify-fail: retry (n из конфига) → `on_fail[]` из перехода → общий recover.
- Recover-цепочка: ESC → клик в свободную область → закрыть окно (если открыто
  не то) → **переоткрыть окно через иконку HUD** (open_market / open_shop_buy /
  open_shop_sell — клик по соответствующей иконке игры + wait verify открытия) →
  перекалибровка якоря → эскалация (пауза + событие стратегии).
- Предусловия открытия: создание лавок в игре допускается не всегда (зона
  торговли, персонаж жив и т.п.). Если после клика по иконке окно не открылось
  за таймаут — это не «сломанный примитив», а штатный FAILED: ядро фиксирует
  состояние (включая возможную модалку с причиной), сообщает стратегии событие
  escalation и не долбит повторными кликами.
- Восстановление раскладки при вводе текста: после набора OCR поля ввода; транслит →
  backspace + switch_layout + повтор (контракт за внешним модулем — мы этот модуль).

### 5.4 API ядра (эскиз, для стратегий)

Синхронные вызовы (из потока/цикла стратегии):
- `open_market()/close_market()`, `open_shop_buy()/open_shop_sell()` — навигация
  окнами: открытие = клик по иконке в HUD игры + `wait_until` сигнатуры окна;
  закрытие = кнопка закрытия окна или ESC (способ выбирается по модели/конфигу).
- `set_tab(name)`, `set_filter(name)`, `search(text)`, `scroll_list(dir, n)` —
  управление обзором.
- `read_rows() -> list[Row]` — чтение видимых строк таблицы (OCR по регионам строк).
- `setup_sell(items: list[(slot, price)])`, `start_sell()/cancel_sell()`,
  `read_shop_state() -> {sold_count, profit, remaining}` — лавка продажи.
- `get_state() -> (window, params)`, `recover()`, `health()`.
События: `on(callback)` / `wait_event(type, timeout)`; журнал событий ведётся ядром
(продано, окно закрыто, модалка, recover-эскалация, kill switch).

### 5.5 Логирование и replay

- Каждое действие: JSONL-запись (кадр-снимок до/после, действие, verify-результат).
- Абстракция `Screen`: `MssScreen` (mss, реальная игра) и `ReplayScreen`
  (записанные кадры/сессия) — стратегии и тесты гоняются на записи без железа.
- **Рекордер сессий** (решение владельца): `RecordingScreen`-декоратор пишет
  каждый кадр + действие + результат в файл сессии при живых прогонах; эти сессии
  — корм для replay-тестов и отладки «без запуска игры».
- FakeHid поверх эмулятора из L2-CRNN-arduino (`tests/fake_device.py`) — юнит-тесты
  без платы.
- Детектор состояний тестируется на 39 существующих скриншотах: для каждого
  ожидаемое `(window, params)` — по мере разметки меты.

### 5.6 Конфиг

`config.yaml`: тайминги/таймауты, порог confidence OCR и число перечитываний при
низком conf, поведенческий профиль (доли способов ввода цены, паузы-джиттеры,
человеческие тайминги HID), пути (модель CRNN, порт arduino), kill switch (хоткей,
таймаут), референсное разрешение.

### 5.7 Выводы builder-check (2026-11-08) и дополнения

Независимая проверка дизайна дала шесть вопросов. Разбор:

1. **Покрытие алфавита CRNN** — проверено частично на живую: чекпоинт
   `runs/20261105-213625/crnn_best.pt` (val exact 0.983) уверенно читает подписи
   окон продажи («Общая прибыль», «Ожидаемая прибыль», «Осталось», «Цена»,
   «Ожидаемые расходы», «Сделка» — conf 0.98–0.999). Числовые значения на слепых
   кропах не проверены — контрольная проверка на доснятых кропах с числами
   (цены, «0 из N», адена) входит в план; guard-тест OCR-обёртки держит набор
   эталонных кропов с известным текстом в `assets/ocr_golden/`.
2. **Геометрия нарезки строк таблицы** (`L2-CRNN-Dataset-Builder`, репозиторий
   теперь доступен и здесь: `E:\L2-CRNN-Dataset-Builder`): в ядро **вендорится**
   код сегментации из `build_dataset.py` — константы геометрии (`COL_SEPS`,
   `ROW_Y0`, `ROW_PITCH`, `MAX_ROWS`, зоны текста колонок) поднимаются в секцию
   `table_geometry` UI-модели, функции (`rows_and_columns`, `extract_cells`,
   `trim_to_text` — цветовая маска текста) переносятся как модуль ядра. Тем самым
   рантайм и обучение используют одинаковую нарезку → OCR не деградирует от
   рассинхрона геометрии. Константы в `build_dataset.py` откалиброваны под скрины
   1136×833 (рамка окна 1003×670) — перекалибровка под референс 1920×1080 делается
   из скриншотов меты на этапе построения модели и закрепляется golden-тестами.
   При переобучении пайплайн датасета получает константы из модели ядра (копия
   с явной пометкой версии, конвертер выводит отчёт об отличиях).
   Также кандидат на вендоринг — `detect_window()` (поиск рамки окна по ярким
   линиям, numpy-only, без шаблонов): используем как первый, дешёвый этап
   детектора якоря «Обзора лавок» до template matching.
3. **Потребление соседних репозиториев**: arduino-модуль — вендорится в репо ядра
   (копия кода с указанием источника; модуль мал и самодостаточен). OCR-модуль
   `L2-CRNN-MODEL-TRAIN` — macOS-only и с абсолютными путями, импортировать его
   нельзя: в ядро вендорится замороженная копия `preprocess` + `ctc_greedy_decode`
   + загрузчик чекпоинта/алфавита (байт-идентично обучающему коду, guard-тест на
   эталонных векторах), сам файл `crnn_best.pt` хранится вне git (LFS/ручная
   копия) и указывается в конфиге.

Остаются два решения за владельцем (зафиксированы в разделе 7) и два пробела
данных: семантика переходов (в meta все `click_leads_to: null`) — описывается
владельцем по знанию игры и досъёмкой; источник кадров для replay-тестов
(сейчас есть только 39 статичных скриншотов) — выбран способ в разделе 8.

## 6. Что оставлено исполнителю (мои решения, помечены как таковые)

- Формат модели: YAML; именование и гранулярность файлов — за исполнителем.
- Template matching: OpenCV `matchTemplate` (TTM_CCOEFF_NORMED) — впервые вводит
  зависимость opencv-python; допустимо, если numpy-only альтернатива ощутимо хуже.
- Структура пакета: плоский `l2core/` с подпакетами `model/`, `detector/`,
  `primitives/`, `scenarios/`, `adapters/`, `api/`.
- Обработка низкого confidence OCR: до N перечитываний с увеличением региона →
  исключение стратегии с диагностикой.
- Позиция скролла определяется кропами «прокрутка вверх/вниз» (есть в мете) плюс
  сравнение нижней видимой строки между кадрами.
- Сценарии пишутся как композиции примитивов, без внутренних состояний — состояние
  всегда спрашивается у детектора, никогда не кэшируется «в голове».
- **AGENTS.md и README — обязательные артефакты репо, создаются в первой же задаче.**
  AGENTS.md — источник истины для будущей работы (людей и агентов): команды
  (тесты, валидация модели, запуск), структура пакета, инварианты, которые нельзя
  ломать молча (никаких sleep — только wait_until; verify на каждое действие;
  никаких абсолютных координат вне слоя якоря; трёхзначный результат критичных
  действий; байт-идентичность вендоренного OCR-препроцесса обучающему коду),
  правила изменений (TDD, детерминизм тестов, код и комментарии на русском,
  как в L2-CRNN-arduino), процесс обновления UI-модели после патчей игры.
  README — быстрый старт для человека: установка, конфиг, dry-run, запуск,
  типичные проблемы. Обновление AGENTS.md — часть DoD каждой задачи, ломающей
  описанное там.


## 7. Интеграция сторонних ревью (2026-11-08, docs/spec_rew/)

Принято из ревью deepseek и qwen (после отсева пунктов, закрытых дизайном, и шума):

### 7.1 Архитектурные дополнения (приняты)

1. **Модель потоков** (закрывает нестыковку «sync API + события»):
   - `action executor` — единственный владелец HID, исполняет действия стратегии;
   - `state observer` — фоновый поток, читает экран, НЕ шлёт действия; именно он
     питает события (продано, окно пропало, модалка);
   - `event dispatcher` — очередь событий; callbacks доставляются в поток стратегии;
   - поток стратегии — единственный, кто вызывает блокирующий API.
   Мониторы/наблюдатели имеют право на внутреннее состояние (базовая линия для
   детекции «продано») — тезис «без внутренних состояний» относится к примитивам.
2. **Трёхзначный результат критичных действий**: `OK` / `FAILED` / `UNKNOWN`.
   UNKNOWN = эффект не подтверждён (лаг, перекрытие). Ядро НЕ повторяет
   потенциально необратимые действия (начать продажу, подтвердить) при UNKNOWN —
   решение за стратегией. Отмена: kill switch прерывает блокирующий вызов,
   возвращает UNKNOWN/CANCELLED, HID освобождается (release_all + курсор в
   безопасную зону).
3. **Статусы окна тоньше, чем no_window**: `not_found` (закрыто/нет на экране),
   `occluded_or_unstable` (якорь мерцает/перекрыто игровым окном/тултипом),
   `found` (шаблон совпал) + отдельный признак «контент прогрузился» (verify
   контентных сигнатур, а не только заголовка). Recover начинается с пассивных
   шагов (ESC, клик по свободной области клиента); клик по заголовку торгового
   окна для подъёма — допустим; ничего не перетаскивать автоматически.
4. **Kill switch, точнее**: остановка = прерывание ожиданий + `hid.release_all()`
   (модуль это умеет) + увод курсора в безопасную точку + событие стратегии.
5. **Dry-run режим**: конфиг-флаг; экран читается, состояние определяется, все
   действия только логируются (без HID). Для первых запусков на живой игре.
6. **Кэш кадра в рамках транзакции**: детектор не переанализирует один кадр
   многократно внутри одного шага (grab → analyze once → решения по свежему кадру;
   перед необратимым действием — свежий grab и re-verify цели).
7. **DPI**: процесс ядра объявляется DPI-aware; в документации — требование
   запуска бота с правами не ниже игры (иначе SetForeground/ввод не сработают).
8. **Конвейер модели**: конвертер из meta.json — «помощник импорта» с явным
   отчётом diff, ручные правки модели он не перезаписывает; шаблоны в `assets/`
   версионируются вместе с моделью; валидатор модели запускается в тестах (CI):
  каждое состояние имеет ≥2 сигнатуры и путь в recover, каждый переход — verify
   и on_fail, rect'ы вписываются в окно.

### 7.2 Контракты, детализированные (принято)

- `Row` (результат read_rows): словарь ячеек по именам колонок модели +
  `screen_y` строки + `icon_hash` (pHash иконки предмета для дедупликации между
  кадрами скролла) + `partial: bool` для обрезанных краевых строк.
- Цены: грамматика региона (разделители `,` `.`, суффиксы `к`/`кк`), валидация
  по диапазону; несовпадение грамматики → перечитывание, при повторе — низкий conf.
- `scroll_list(dir, n)` — единица n = щелчок колеса; конец списка определяется
  признаком из модели (состояние стрелки «вниз» disabled / пустая область), не
  только сравнением строк.
- События: типы `sold`, `window_closed`, `modal`, `recovered`, `escalation`,
  `killed`; полезная нагрузка фиксируется в API-справочнике (пишется вместе с кодом).
- `slot` (для setup_sell): координаты ячейки сетки лавки из модели сетки
  (генерируются из геометрии сетки, не размечаются вручную).

### 7.3 Чек-лист реализации из ревью (принято в план как задачи/тесты)

hover меняет вид элемента до клика (verify после hover-паузы); тултип может
перекрыть цель (сдвинуть курсор/подождать исчезновения); мигающая каретка ломает
OCR поля (стабилизировать кадр: два подряд одинаковых чтения); плейсхолдер vs
введённый текст; «резиновый»/инерционный скролл; одинаковые строки (дедуп по
icon_hash+цена+y); рынок меняется во время сканирования (read_rows возвращает
snapshot_id, стратегия сверяет); контент не прогрузился сразу после открытия
(verify контентных сигнатур); SetForeground может не сработать (retry + эскалация);
заблокированный экран / оверлеи → осмысленная ошибка, не слепые клики;
ограничение размера логов кадров (ротация, только ключевые кадры).

### 7.4 Отклонено (с причиной)

- Полный отказ от внутреннего состояния — нереален для мониторов событий (см. 7.1.1).
- «Считать no_window всегда закрытым окном» — противоречит реальности внутриигровых
  окон (см. 7.1.3).
- Мультимасштабный template matching под разные разрешения — окна торговли не
  масштабируются (подтверждено владельцем); другие разрешения — заявлены как
  «пока только этот экран», рекалибровка шаблонов — досъёмка при переезде.

## 8. Проверка (DoD)

- Юнит-тесты: примитивы на FakeHid/FakeScreen; парсер модели; конвертер меты.
- Интеграционные (replay): сценарии обхода/выставления/мониторинга прогоняются на
  записанных кадрах; assert на последовательности состояний и OCR-результатов.
- Трассировка use-cases по графу переходов: ни одного перехода без verify/on_fail;
  unknown достижим отовсюду и имеет выход; ни одной абсолютной координаты вне
  слоя якоря.
- Ручной прогон на живой игре (пользователь): обзор, поиск, скролл, выставление
  лавки, мониторинг, recover по kill switch.
- AGENTS.md и README созданы, актуальны и покрывают запуск, тесты и правила
  изменений (см. раздел 6).
- Тесты конфликта сигнатур (признаки противоречат друг другу → unknown, не
  уверенное решение), тесты таймаутов/лагов (трёхзначный результат).
- OCR-бенчмарк на golden-наборе (точность/время на CPU и GPU).
- Dry-run прогон на живой игре (без HID): состояния определяются, действия
  логируются.
