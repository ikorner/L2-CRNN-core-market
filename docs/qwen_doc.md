1. Рамка и зафиксированные решения. Ядро = UI-драйвер трёх окон: «Обзор лавок», «Торговая лавка (Купить)», «Торговая лавка (Продажа)». Оно знает состояния и контролы, выполняет операции с проверкой результата и отдаёт наверх стабильный API; торговая стратегия, маршрутизация, дедупликация и id предметов — вне ядра (стратегия — отдельный меняемый проект). Распознавание (текст, цифры, грамматика цен, цвета) — отдельный модуль с контрактом read(region) → (value, confidence); ядро не знает грамматики. mss остаётся внутри ядра (кода мало), arduino и OCR — внешние модули с известным API; антидетект уже встроен в уровень arduino. Сейчас состояния ничем не детектируются — спека обязана ввести детектор. Всё знание об UI выносится в машиночитаемую UI-модель (states/elements/transitions), ядро — её интерпретатор: патч клиента = правка модели, смена стратегии = другие вызовы API, код ядра не меняется.
2. Формализм UI-модели. Состояние = signature (визуальные предикаты от дешёвых к дорогим: пиксель-проба → шаблон → OCR; минимум два независимых: заголовок окна + счётчик/характерный элемент) + доступные контролы + исходящие переходы; из любого состояния есть переход в unknown по таймауту. Элемент = карточка: rect от якоря окна в reference-разрешении, визуальные варианты (normal/hover/pressed/disabled/active) с кропами-шаблонами на каждый, способ фокуса/клика/очистки/ввода и обязательная верификация каждого действия (focus verify, text verify через OCR-контракт), побочные эффекты. Переход = (состояние, действие) → (целевое состояние, verify-предикат, timeout, on_fail[]); побочные эффекты фиксируются явно: таб сбрасывает подтабы на свой набор, «Обновить» сбрасывает скролл, стрелка между панелями переносит ячейку и меняет счётчик (n/6)/(n/5), «Начать покупку/продажу» disabled при пустом списке, вихрь строки «Продажа» открывает shop_buy, строки «Покупка» — shop_sell. Известные состояния: market.list / market.empty («Нет предметов, соответствующих условиям.») плюс подсостояния табов, подтабов, фильтров и поиска; shop_buy.empty/filled; shop_sell.empty/filled; системные модалки; unknown. Протоколы: ожидание по предикату вместо sleep, ретраи, recover из unknown (цепочка ESC/закрыть/переоткрыть/рекалибровка), аварийные стопы.
3. Материалы (досье), которые готовим руками. Заморозить reference-разрешение и масштаб. Скриншоты полных окон с рамкой по чек-листу: market — все табы и подтабы, пусто/заполнено, скролл топ/середина/конец, поле поиска placeholder/focused/filled, фильтры Продажа/Покупка; shop_buy и shop_sell — пусто, заполнено, disabled confirm, вид после подтверждения; системные модалки; «голый» клиент. Разметка: нумерованные rect'ы в JSON (id = window.element), кропы id_variant.png, отметки точек клика. Плюс API модулей arduino/ocr и скриншот-хелпера с сигнатурами и_latencies; 2–3 заполненные карточки элемента и 3–4 перехода как эталон стиля; список use-cases ядра для стратегии (открыть/закрыть окна, get_state, таб/подтаб/фильтр, ввести и применить поиск, прочитать видимые строки, проскроллить, открыть лавку из строки, добавить ячейку в список, прочитать итоговую цену, подтвердить/отменить, recover).
4. Пакет агенту и протокол работы. Пакет: README с рамкой и non-goals; API модулей; досье скриншотов + таблица элементов; эталоны; use-cases; требования к спеке и DoD; протокол. Протокол: (1) агент изучает и возвращает не спеку, а вопросы с гипотезами плюс заказы на измерения и досъёмку (задержки открытия окон, hover- и disabled-варианты, вид после подтверждения); (2) ты отвечаешь и доснимаешь; (3) агент пишет черновик спеки + UI-модель YAML; (4) агент сам трассирует каждый use-case по графу и выдаёт отчёт о дырках (переходы без verify, состояния без выхода); (5) твоё ревью. Структура спеки: scope/non-goals; архитектура (интерпретатор модели + примитивы + контракты); UI-модель; протоколы ожиданий/ретраев/таймаутов; unknown и recover; контракт распознавания; API ядра; логирование и replay-прогон на записанных кадрах без arduino; конфиг; тесты и приёмка; процесс обновления модели после патчей. DoD: use-cases трассируются без разрывов; у каждого перехода есть verify и on_fail; ни одной абсолютной координаты вне якорей; ни одного OCR-вызова мимо контракта; unknown достижимо отовсюду и имеет выход; аварийные стопы определены.
