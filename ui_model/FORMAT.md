# Формат YAML UI-модели (задача 2.1)

UI-модель — декларативное описание окон торговли: «где и как выглядит»
(design.md, решение 1). Потребители: конвертер (2.2), валидатор (2.3),
table_geometry (2.4), детектор состояний (3.4–3.5), грамматики OCR (4.4),
сценарии (6.x). Читаемость для человека-разметчика важнее лаконичности схемы.

## Гранулярность файлов (зафиксированное решение)

- `ui_model/common.yaml` — общий словарь: варианты элементов, роли,
  грамматики OCR. Не является моделью окна.
- `ui_model/<window>.yaml` — одна модель на окно, `<window>` — одно из
  `market`, `shop_buy`, `shop_sell`.
- `ui_model/navigation.yaml` — навигационная модель (не окно): открытие
  окон через «Меню»/quick-slot, формат — ниже.

Каждая модель окна обязана содержать секции `window`, `elements`, `states`,
`transitions`, `ocr_regions`; `table_geometry` — для окон со списком
(обязательность по конкретному окну проверяет валидатор 2.3, парсер
принимает модель и без неё); `grid_geometry` — опциональная (иконная
сетка слотов, 6.2).

Неизвестные ключи на любом уровне отклоняются парсером — опечатка
разметчика не должна молчать.

## Координаты

Все координаты — пиксели референсного разрешения 1:1, без масштаба.

- `rect` обычного элемента — от якоря своего окна (решение 4).
- `search_area` HUD-элемента (`hud: true`) — допустимая область поиска
  в клиентской области игры, а не фиксированное смещение: панели игры
  перетаскиваются, HUD ищется template matching'ом по этой области.
- `click_point` — в системе координат родительского поля элемента
  (от якоря окна для `rect`, от угла `search_area` для HUD).
- Шаблоны (`template`) — пути относительно каталога `assets/` ядра.

## window

```yaml
window:
  id: market            # market | shop_buy | shop_sell
  title: "Обзор лавок"  # подпись окна (поиск якоря, диагностика)
  size: [w, h]          # размер окна в референсе (вписывание rect'ов)
```

## elements

Словарь `id -> элемент`. Роли: `click_target`, `ocr_region`,
`state_signature`, `icon_sample`. Роли-сырьё meta.json (`decor`,
`ocr_ground_truth`) в модель ядра не переносятся — это данные датасета.

```yaml
elements:
  tab_home:
    rect: [x, y, w, h]     # от якоря окна
    role: click_target
    variants:              # кроп-шаблон на вариант
      normal: {template: market/tab_home_normal.png}
      active: {template: market/tab_home_active.png, click_point: [x, y]}
  market_pic:              # HUD-элемент навигации
    role: icon_sample
    hud: true
    search_area: [x, y, w, h]  # область поиска в клиентской области игры
    variants:
      normal: {template: hud/market_pic.png, click_point: [x, y]}
```

Варианты (`normal`, `hover`, `pressed`, `disabled`, `active`,
`placeholder`, `focused`, `filled`) — словарь из `common.yaml`.

## states

Параметризованные состояния `(window, params)` (решение 9): сигнатуры
отделены от значений параметров. Признаки-сигнатуры образуют иерархию
`pixel_probe → template → ocr`; минимум два независимых признака на
состояние проверяет валидатор 2.3. Пустая секция допустима для начального
импорта конвертером (2.2) — до ручной разметки сигнатур.

```yaml
states:
  list_home:
    params:              # свободный словарь строк
      tab: home
    signatures:
      - {kind: pixel_probe, points: [{at: [x, y], color: [r, g, b]}]}
      - {kind: template, element: tab_home, variant: active}
      - {kind: ocr, region: window_title, expect: "Обзор лавок"}
```

Проверка (check) — один из трёх видов, обязательные поля по виду:

- `pixel_probe`: `points` — список `{at: [x, y], color: [r, g, b]}`;
- `template`: `element` (id элемента), `variant` (вариант элемента);
- `ocr`: `region` (id OCR-региона), `expect` (ожидаемый текст).

## transitions

Простые переходы декларативно: `(state, action) -> (expected, verify,
timeout, on_fail[])`. Действие — `click` (поле `element`) или `key`
(поле `key`). `timeout` опционален: не задан — берётся из конфига при
исполнении. Шаги `on_fail` — только именованные шаги исполнителя
(`press_esc`, `click_free_area`; семантика — код recover-примитивов);
координатные действия в переходах недопустимы — точки кликов
происходят из `rect`/`click_point` элементов (слой якоря). Словарь шагов
и полный обход графа (unknown достижим отовсюду и имеет выход)
проверяет трассировка (задача 6.5, `l2core.model.trace`, тесты CI);
непустоту `verify`/`on_fail` требует парсер.

```yaml
transitions:
  - from: list_home
    action: click
    element: tab_equipment
    expected: list_equipment
    timeout: 5.0
    verify:
      - {kind: template, element: tab_equipment, variant: active}
    on_fail: [press_esc, click_free_area]
```

## ocr_regions

Словарь `id -> регион`; `grammar` — имя грамматики из `common.yaml`.
Пустая секция допустима для начального импорта конвертером (2.2) — до
ручной разметки регионов.

```yaml
ocr_regions:
  window_title:
    rect: [x, y, w, h]   # от якоря окна
    grammar: text
  price_cell:
    rect: [x, y, w, h]
    grammar: price
  search_field:          # поле ввода
    rect: [x, y, w, h]
    grammar: text
    placeholder: 'Введите\s+название'  # опционально: regex плейсхолдера
```

`placeholder` — опциональный regex-паттерн текста пустого поля ввода.
Стабилизатор мигающей каретки (задача 4.5) возвращает для совпавшего с
паттерном (или пустого) текста status `placeholder` и value `None` —
плейсхолдер ≠ введённый текст. Паттерн проверяется `re.search` против
сырого прочитанного текста; в модели не задан — данных о плейсхолдерах
нет (docs/OWNER_QUESTIONS.md, Q23).

## table_geometry

Константы нарезки таблицы (общие с пайплайном обучения, решение 12):

```yaml
table_geometry:
  col_seps: [x1, x2, ...]   # x разделителей колонок, от якоря окна
  row_y0: y                 # y первой строки (от якоря окна)
  row_pitch: p              # шаг строк
  max_rows: n
  columns:                  # зоны текста внутри ячейки колонки
    item:  {zone: [x, y, w, h], grammar: text}
    price: {zone: [x, y, w, h], grammar: price}
```

Семантика `zone` (зафиксировано в 2.4): `x` — от якоря окна, `y` — от
верха строки (нумерация строк — через `row_y0`/`row_pitch`). Колонки
накладываются на соседние `col_seps`: колонка с индексом i занимает
`col_seps[i]..col_seps[i+1]`, зона текста вписывается внутрь. У окон,
чьи «списки» — иконные сетки без текстовых колонок (shop_buy/shop_sell),
секция не задаётся (состав окон с текстовой таблицей —
`WINDOWS_WITH_LISTS` валидатора). Константы выгружаются для
датасет-пайплайна через `python -m l2core.model.export_geometry`
(Python-модуль с пометкой версии и diff-отчётом).

## grid_geometry

Опциональная секция: параметрическая геометрия иконной сетки слотов окна
(лавка: ячейки под предметы, drag-перенос; потребитель — сценарий
setup_sell, 6.2). Координаты — от якоря окна, как у `rect` элементов:

```yaml
grid_geometry:
  origin: [x, y]    # верхний левый угол ячейки (0, 0), от якоря окна
  pitch: [dx, dy]   # шаг между соседними ячейками (оба > 0)
  cell: [w, h]      # размер ячейки (положительный)
  cols: n           # число колонок (> 0)
  rows: m           # число строк (> 0)
```

Нумерация слотов row-major: `slot = row * cols + col`; центр ячейки
вычисляет генератор слоя сценариев (`slot_point` в
`l2core/scenarios/setup_sell.py`), в формате только константы (как у
`table_geometry`). Валидатор проверяет вписывание крайних ячеек сетки в
окно (`grid_in_window`). В отгруженной модели `shop_sell` секция не
размечена (сырьё поле `slot` не описывает — KNOWN_GAPS): до калибровки
константы сетки передаются сценарию параметром.

## Навигационная модель (`ui_model/navigation.yaml`)

Файл `navigation.yaml` — НЕ модель окна: секций `window`/`states`/
`transitions` в нём нет, парсер моделей окон (`load_model`) его не
принимает. Содержит навигацию открытия окон торговли — «Меню»
(клавиша X / гамбургер) и панель быстрого доступа (quick-slot):

- `elements` — элементы в формате элементов окон: HUD-элементы
  (`hud: true`, `search_area` в клиентской области игры; меню и панель
  перетаскиваемы/фиксированы — позиция не кэшируется), элементы внутри
  «Меню» — `rect` 1:1 от HUD-якоря `menu_anchor` (инвариант 3).
- `signatures` — именованные наборы проверок (минимум два признака, как
  у состояний окон; `menu_open` — открытое «Меню»).
- `recipes` — рецепты открытия окон. Рецепт: `opens` (целевое окно),
  непустые `steps` и `on_fail`, опциональный `alternate` (резервный
  рецепт). Шаг: `action: key|click`; `key`-шаг требует `key` (имя из
  KEYCODES) и запрещает `element`, `click`-шаг — наоборот; `verify` и
  `on_fail` обязательны; опционально `when: [checks]` (выполнять шаг
  только если проверки сошлись на текущем кадре) и `skip_if: [checks]`
  (пропускать, если сошлись). Элемент списка `verify`/`when`/`skip_if` —
  mapping проверки или строка-ссылка на сигнатуру (разворачивается в
  её проверки). Проверки: `template` (с опциональным отрицанием
  `expect: absent`) и `pixel_probe`; `ocr` в навигации не поддержан.

Связка с окнами — соглашение имён: рецепт `open_<window>` открывает
окно из глобального состояния `recover_closed` (живёт в модели market);
трассировка (6.5) проверяет достижимость каждого окна через рецепт.
Исполнение — `l2core.primitives.navigation` (run_recipe) поверх
примитивов; оценка проверок — `l2core.detector.navchecks`
(build_nav_evaluator), без якоря окна торговли (меню открывается при
закрытом окне). Координатных действий в рецептах нет — точки кликов
происходят из `rect`/`click_point` элементов и template-поиска по
`search_area`. Валидация — `validate_navigation` (те же правила
осмысленности, что у валидатора окон).

## common.yaml

```yaml
variants: [normal, hover, pressed, disabled, active, placeholder, focused, filled, open]
roles: [click_target, ocr_region, state_signature, icon_sample]
grammars:
  digits: {kind: digits}
  price: {kind: price, separators: [",", "."], suffixes: {"к": 1000, "кк": 1000000, "тыс": 1000, "млн": 1000000, "млрд": 1000000000}, units: [аден]}
  text: {kind: text}
```

Виды грамматик: `digits` (только цифры), `price` (разделители, суффиксы
`к`/`кк` и составная игровая запись), `text` (свободный текст). Парсер
может работать и без явного
`common.yaml` — тогда используется встроенный словарь, совпадающий с
поставляемым `common.yaml` (проверяется тестом).

Опциональные поля грамматик (задача 4.4, разбор и валидация —
`l2core/model/grammars.py`):

- `min`/`max` — целые неотрицательные границы допустимого диапазона
  значения (только `digits` и `price`; `min <= max`). Не заданы —
  дефолт: `price` — 1..2^63-1 (адена не бывает нулевой), `digits` —
  0..2^63-1 («0 из N»). Конкретные игровые границы — см.
  `docs/OWNER_QUESTIONS.md`.
- `units` — список единиц измерения (только `price`), отсекаемых
  перед разбором по границе слова, регистронезависимо
  (например, `units: ["аден"]`: «240 аден» -> 240).

Семантика `price`: разделитель — разрядная группа, если все группы
после первой ровно по 3 цифры (`1,500` -> 1500), иначе — десятичная
дробь, допустимая только с суффиксом и обязанная дать целое после
умножения на множитель (`1.5кк` -> 1500000). Суффикс матчится самый
длинный из заданных.

Составная игровая запись цены (формат подтверждён владельцем, Q22):
последовательность пар «число масштаб», где слово-масштаб — ключ
`suffixes` длиной ≥ 3 (`5 млрд 450 млн 300 тыс 100 аден` ->
5_450_300_100; старшие части при малой цене отбрасываются: `5 тыс
100 аден` -> 5100). Части суммируются, масштабы обязаны идти строго
по убыванию, повторы и вставки вне формата — несовпадение (голое
число в середине последовательности, например `5 100 тыс`, —
несовпадение: вероятно, OCR потерял слово, а молчаливый разбор
заниженной цены недопустим). Хвостовое голое число — неявные адены
(«аден» при этом — `units` и отсекается до разбора). Регистр слов
не учитывается. Классический разбор (разделители, суффиксы `к`/`кк`)
действует на тексты без слов-масштабов и не изменился.

Несовпадение грамматики или выход за диапазон —
перечитывание с увеличением региона (сигнал «не сошлось» — статус
`invalid`, `confidence=0.0`); цикл из N перечитываний и порог
confidence — задача 4.5.

## Ошибки формата

Любая ошибка структуры — `l2core.model.ModelFormatError` с именем файла,
секцией и деталью (сообщение на русском). Падение загрузки обязательно;
«починить модель» — задача разметчика, не рантайма.

## Валидация инвариантов (задача 2.3)

Формат проверяет парсер (`l2core.model.loader`); инварианты спеки ui-model
— валидатор (`l2core.model.validator`, CLI:
`python -m l2core.model.validator <файлы...>`): минимум две сигнатуры на
состояние, путь в recover-состояние (id с префиксом `recover`) по графу
переходов, семантика переходов и проверок, rect'ы в окне, шаблоны в
`assets/`, `table_geometry` у окон со списком. Валидатор подключён в
тестовый набор; известные незакрытые пробелы отгруженных моделей явно
записаны в `ui_model/KNOWN_GAPS.yaml` — тест гоняет валидатор по
моделям и требует, чтобы список пробелов совпадал с фактическими
нарушениями (лишняя запись и нарушение вне списка падают).
